# Keys: play-once vs repeat + UI clarity pass

## Context

Debug session findings (today): the MPK mini's keybed intermittently sends **no note events** while knobs/pads keep streaming — almost certainly the controller's **onboard arpeggiator** (ARP button next to the pads; it also produces the "same note repeating on one press" you described). addu94 never sends MIDI clock, so an engaged arp can hold the keybed hostage. Separately, the app's keys path is the only one gated (`play_engine.cpp:520`), which is why pads always survive.

Your requests:
1. **An option for a key to play once vs multiple times** — implemented as an app-side retrigger guard: in "once" mode, a NoteOn for an already-held note (same channel, no NoteOff between) is ignored, so hardware-arp repeats never retrigger the synth.
2. **More names and definitions in the UI** — the FX panel uses jargon ("downsmp", "thresh"), every panel has exactly one terse tooltip, and nothing explains what things do.

## Part 1 — Keys play-once guard

**New pure struct** `src/music/retrigger.hpp` (namespace `addu94::music`, header-only, follows arp/scale style there):
- `RetriggerGuard`: fixed pre-allocated state `std::array<std::array<std::uint64_t, 128>, 16> last_on_ns_` (16 ch × 128 notes, ~16 KB, zero allocation).
- `bool allow(int channel, int note, bool is_note_on, std::uint64_t now_ns)` — when active: genuine NoteOn (`d2 > 0`) within `kStuckNs = 5 s` of the last NoteOn for that (channel, note) is suppressed; after 5 s the mark self-expires (protects against hardware all-notes-off unlatching without individual NoteOffs). Any note-off form (`NoteOff` **or** NoteOn-vel-0, per `midi/types.hpp:50-54` semantics) clears the mark. Inactive mode = always allow.
- Default **active** ("once") — matches how a keybed should behave; toggle restores pass-through.

**Engine wiring** (follows the `arp_on_`/`scale_lock_` pattern exactly):
- `src/app/play_engine.hpp`: `music::RetriggerGuard retrigger_;` + `std::atomic<bool> keys_play_once_{true};` near hpp:369; getter/setter pair `keys_play_once()/set_keys_play_once(bool)` near hpp:266.
- `src/app/play_engine.cpp` in `PlayEngine::on_midi` keys branch (~line 520): consult `retrigger_.allow(...)` before `push_voice` (MIDI thread — wait-free, no allocation). Note-offs still pass so voices release. The `event_q_` forwarding at line 531 stays untouched (mapping/recorder unchanged).
- **UI toggle chip** in `src/ui/controller_mirror.cpp` status column (follows `paint_chip` at controller_mirror.cpp:219-248 and the mode-strip click pattern at :490-498): a `[keys] ONCE / REPEAT` chip that calls `engine_.set_keys_play_once(...)`, reflecting current state each paint (30 Hz tick).
- `src/mapping/actions.hpp`: add `Action::KeysPlayOnceToggle` after `ScaleLockToggle` (line ~53) + `to_string` case `"keys.play_once"` (~line 101); one `case A::KeysPlayOnceToggle:` line in `PlayEngine::command()` after `ScaleLockToggle` (play_engine.cpp:1177-1181). This keeps the action addressable for future MPK binding without changing current mapping behavior.

**Test**: new `tests/test_retrigger.cpp` (follows `test_framework.hpp` TEST/CHECK style of test_mapping.cpp): first NoteOn allowed, immediate repeat suppressed, note-off clears, vel-0 NoteOn clears, 5 s expiry re-allows, inactive mode allows everything. Append stem to the `foreach` in `tests/CMakeLists.txt:4`.
